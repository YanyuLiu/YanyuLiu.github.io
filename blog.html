AI Safety Is a Systems Measurement Problem

Recent AI safety incidents around autonomous agents got me thinking about what a data scientist can actually contribute to safety.

As agents gain access to browsers, code, files, and external tools, safety is no longer just about whether a model generates a harmful response. A model can make a reasonable-looking decision at each step and still end up taking an action the user never intended.

From a DS perspective, three things stood out to me.

1. Measure the chain of failure

An unsafe outcome usually happens through a sequence:

Exposure → Model decision → Tool call → Action → Harm

Instead of measuring only the final incident rate, I would decompose the probability of harm:

\[ \begin{aligned} P(H) ={}& P(E) \times P(F \mid E) \\ &{}\times P(A \mid F) \times P(H \mid A) \end{aligned} \]

where \(E\) is exposure to a risky situation, \(F\) is the model following the unsafe path, and \(A\) is the action actually being executed.

This changes how we think about mitigation. We don't necessarily need one perfect safety layer. If the model misses something, permissions, sandboxing, monitoring, or action-level controls can still break the chain.

More importantly, this decomposition tells us where the system is actually failing and where another unit of engineering effort is most valuable.

2. Measure expected harm, not incident count

Not every safety incident has the same consequence.

A bad response, an unauthorized email, and an agent deleting production data shouldn't each count as “one incident.”

A simple starting point is:

\[ \begin{aligned} \mathrm{Expected\ Harm} ={}& \sum_i P(H_i) \\ &{}\times \mathrm{Severity}(H_i) \end{aligned} \]

And at the system level, I might think about risk as:

\[ \begin{aligned} \mathrm{Risk} ={}& \mathrm{Exposure} \times \mathrm{AttackRate} \\ &{}\times \mathrm{SuccessRate} \times \mathrm{Severity} \end{aligned} \]

This also makes the denominator important. If agent usage grows 10x, the number of incidents may increase even while the system becomes safer.

So instead of asking only “How many incidents did we have?”, I would also ask:

How much expected harm are we generating per risky opportunity?

3. Treat human confirmation as a scarce resource

One common safety solution is to ask the user before an agent takes a potentially sensitive action.

But confirmation has diminishing returns. If an agent asks for approval twenty times a day, users will eventually learn to click “Allow” without reading.

So I would treat user attention almost like a limited safety budget.

For example:

\[ \mathrm{Loss} = \mathrm{ExpectedHarm} + \lambda \cdot \mathrm{UserFriction} \]

The goal isn't to minimize confirmation prompts or maximize them. It's to decide where confirmation actually changes behavior.

Low-risk, reversible actions might happen automatically. Medium-risk actions might require confirmation. High-risk or irreversible actions may need stronger controls—or simply shouldn't be executable.

That creates an interesting DS problem: estimate the marginal safety value of each intervention and spend user attention where it has the highest return.

What I find interesting about recent AI safety incidents is that they make safety look increasingly like a systems measurement problem.

The model matters, but so do the layers around it: permissions, tools, monitoring, human attention, and the way we define harm in the first place.

For data scientists, the opportunity may be less about building one perfect “safety metric,” and more about figuring out where risk enters the system, how it propagates, and which intervention actually breaks the chain.
